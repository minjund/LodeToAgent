# 스케치 003: Causal Spine Workbench

## 디자인 질문

002에서 선택한 **A · 인과선**을 제품의 중심으로 유지하면서, 여러 AI 세션과 현재 LoadToAgent에 구현된 전체 기능을 어떻게 붙여야 “완전하지만 복잡해 보이지 않는” 화면이 되는가?

## 철학

**완전함은 모든 기능이 동시에 보이는 상태가 아니라, 모든 기능의 위치를 예측할 수 있는 상태다.**

1. **관찰**은 세션별 인과선에서 시작한다. 각 줄은 하나의 작업이며 메인 에이전트 → 서브에이전트·PowerShell → 결과가 앱의 기본 문법이다.
2. **여러 세션은 병렬 레인으로 쌓는다.** 가장 중요한 세션 하나만 펼치고 나머지는 축약하되, 실행·오류·승인·멈춤 신호는 숨기지 않는다.
3. **판단**은 주황 신호 한 종류로 모은다. 승인·거절·재할당·실패 대응은 `확인할 일`에서 처리한다.
4. **개입**은 대상을 선택한 뒤 열린다. 대화·과정·사용량·증거·중단·재시도·터미널은 선택한 노드의 문맥을 이어받는다.
5. **관리**는 작업 흐름 밖에 둔다. 예약, 터미널, tmux, 설정은 동일한 앱에 있으나 홈의 시선을 차지하지 않는다.
6. **무거운 도구는 공간을 빌린다.** 터미널과 tmux가 열릴 때만 넓은 작업면을 사용하고, 닫으면 인과선으로 돌아간다.

## 변형

- **A: 컨텍스트 도크** — 좌측 기능 레일, 중앙 인과선, 선택 시 우측 상세 도크. 터미널·tmux 같은 무거운 기능은 중앙 작업면을 교체한다. 현재 Electron 구조에 가장 가깝고 반응형 위험이 낮아 추천한다.
- **B: 하단 명령 데크** — 인과선은 항상 남기고 전체 기능을 하단 데크에서 펼친다. 한 화면 연속성은 좋지만 세로 공간과 모바일 대응이 어렵다.
- **C: 분할 관제** — 인과선과 선택한 기능을 항상 좌우로 함께 보여준다. 동시 관찰에는 강하지만 작은 화면과 고밀도 그래프에서 인과선이 좁아진다.

## 확인할 것

- 좌측 레일만 보고 전체 기능의 위치를 예측할 수 있는가?
- 홈에 돌아왔을 때 인과선이 즉시 시선의 중심으로 복구되는가?
- 서브에이전트와 PowerShell 상세가 서로 다른 문법으로 열리는가?
- 대화 → 터미널, 실행 노드 → 출력, 확인 요청 → 승인·재할당의 이동이 끊기지 않는가?
- 전체 작업, 예약·실행 단계, 터미널, tmux, 설정이 홈의 인지 부하를 늘리지 않는가?

## 추천

첫 구현은 **A: 컨텍스트 도크**를 권한다. 현재 앱의 화면 전환·drawer·terminal workbench 구조를 재사용하면서도, 홈의 기본 화면을 인과선으로 단순화할 수 있다.
