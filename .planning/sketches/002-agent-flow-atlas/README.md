# 스케치 002: Agent Flow Atlas

## 디자인 질문

메인 에이전트 → 서브에이전트·PowerShell → 결과라는 인과관계를 사용자가 3초 안에 이해하려면 무엇을 화면의 중심에 두어야 하는가?

## 철학

이 화면은 대시보드가 아니라 **관계의 지도**다.

1. **작업은 카드의 집합이 아니라 인과관계다.** 누가 시작했고, 누구에게 위임했고, 어떤 명령이 현실을 바꿨는지가 한 문장처럼 읽혀야 한다.
2. **에이전트는 생각하고, PowerShell은 행위하며, 결과는 기억한다.** 세 종류를 색보다 형태·아이콘·문장 구조로 먼저 구분한다.
3. **모든 것은 보이되 모든 것이 소리치지는 않는다.** 현재 실행과 인간의 판단만 강하게, 완료 기록은 낮은 대비로 남긴다.
4. **색은 장식이 아니라 의무다.** 민트는 움직임, 주황은 사람의 판단, 회색은 완료된 증거만 뜻한다.
5. **상세는 선택 이후에 나타난다.** 첫 화면은 흐름을 보존하고, 클릭한 노드의 대화·명령·출력만 옆에서 열린다.

## 변형

- **A: 인과선** — 메인 에이전트에서 서브에이전트와 PowerShell로 갈라지고 결과로 합쳐지는 한 개의 흐름 캔버스. 핵심 기능에 가장 직접적이라 추천한다.
- **B: 흐름 장부** — 모든 실행 단위를 행으로 정리해 프로젝트와 에이전트가 많아질 때의 밀도를 우선한다.
- **C: 시간 레인** — 각 실행 단위를 시간축 위에 놓아 언제 위임되고 언제 끝나는지 읽게 한다.

## 무엇을 찾아봐야 할 것

- 3초 안에 메인 에이전트, 서브에이전트, PowerShell을 구분할 수 있는가?
- 각 실행 단위의 현재 문장이 상태 배지보다 먼저 읽히는가?
- 완료된 작업이 사라지지 않으면서 현재 작업을 방해하지 않는가?
- 프로젝트가 10개, 실행 단위가 30개로 늘었을 때 어떤 변형이 가장 덜 무너지는가?
- 노드를 눌렀을 때 상세 정보가 흐름을 가리지 않고 자연스럽게 이어지는가?

## 추천

첫 구현 방향은 **A: 인과선**을 권한다. 현재 제품의 핵심 차별점인 “메인 → 위임/명령 → 결과”를 가장 적은 학습 비용으로 드러낸다. 다만 20개 이상의 동시 실행을 다루는 고밀도 모드는 B의 행 구조를 보조 보기로 결합하는 것이 좋다.
